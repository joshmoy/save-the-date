# Retention, archives and deletion

Run normal `pnpm dev:api` and `EMAIL_ADAPTER=capture pnpm dev:worker` locally. The worker sweeps expiry once per minute. Owners see exact expiry/review/grace dates under Settings. Archive requests have durable idempotency and individual failed-export retries. Download `.tar` and extract with a standard archive tool (`tar -xf wedding-archive.tar`); inspect `wedding.json` for source records, checksums and omitted/unavailable originals.

Production must supply a private `DELETION_LEDGER_ROOT` on a separately retained volume, or `DELETION_LEDGER_S3_BUCKET` on a separate private bucket. Never roll this ledger back with the database/object snapshot. S3 archives need multipart permissions (create/upload/complete/abort); workers need temporary disk for the full output plus resumable private staging. Live media has its own 10 GiB allowance; archive staging needs additional capacity.

Before restoring: keep public/API/worker traffic stopped, restore database and private object inventory using supported PostgreSQL tools, retain the current deletion ledger and keys, run migrations, and start the API in isolation. Startup replays ledger quarantine before opening routes. Run the worker's erasure reconciliation, verify grants/pass status and private object absence, reconcile post-backup admissions, then reopen traffic. Never treat an old admission snapshot as authoritative without reconciliation.

Backups: encrypt and retain daily snapshots for at most thirty days, with access logging and off-host copies. Age out obsolete objects/config/key backups on the same schedule; operational audit events have a twelve-month schedule (superseding the earlier ninety-day implementation). Minimal deletion markers and hashed retired slugs persist to prevent older-snapshot resurrection. This local fixture replay is not the complete multi-adapter disaster-recovery release drill.

Do not run deletion on existing wedding data for testing. Use a disposable `_test` database and synthetic fixtures. The API does not export unverified/unsafe originals; the manifest explains omissions. Already downloaded guest copies cannot be recalled. External email/AI provider erasure is limited to locally held references and provider-supported deletion; no unauthorised external calls are performed.

Legacy content in exports: `wedding.json` includes `records.std_legacy_content`, containing the validated source wording, historical post dates, collection metadata and external media references, with the original source checksum and import time. Referenced files are not presented as downloaded/processed originals. Unknown or malformed legacy source metadata is excluded with `legacySourceOmissions: [{code: "LEGACY_SOURCE_REQUIRES_REVIEW"}]`; raw legacy credentials are never copied into the archive. Review those omissions against the separately encrypted migration backup. Default exports still exclude private attendee/RSVP/admission data; sensitive exports retain their explicit opt-in and recent-authentication requirements.

Optional RSVP answer deletion is recovery-safe. The API requires the independent resource-erasure ledger, clears the selected event's existing optional answers, immediately revokes older sensitive archives and queues their private output/staging cleanup as `rsvp-answer-delete`. Ordinary archives remain available. Monitor failed/stalled cleanup jobs and retry their normal worker transport; do not restore deleted archive rows to repair a failed download. Create a fresh export instead. Restore startup replays the cutoff marker before access and recreates cleanup work for restored files; later answers are preserved. Deploy compatible API/worker binaries together. The platform cannot retract files already downloaded by owners.

Pilot schedule alignment (TRD §14): the worker minute sweep clears optional meal/dietary/accessibility/note answers ninety UTCdays after event end, with start fallback; undated events wait for a real date or owner deletion. It disables collection and uses the same independent markers/archive cleanup as manual erasure. Batches are bounded to1000 due events per sweep; monitor worker failures/backlog, especially ledger outages. API response collection and guest question projections close optional fields at the deadline even before the next sweep. Correct the schedule before enabling questions for a genuinely rescheduled event. Audit events now expire after twelve months; resolved support reports/provider inboxes still expire after ninety days. Earlier documentation's ninety-day operational-audit schedule is superseded. Previously purged logs cannot be recreated.

Watch structured `worker.maintenance_failed` events with task `retention`; no answer/contact/path values are logged. A failed sweep retries on the next minute while unrelated jobs continue. Startup restoration quarantine/reconciliation remains mandatory and is not bypassed by this periodic-task isolation.
