# Guest access and RSVP

Run `pnpm db:migrate`, `pnpm dev:api`, `pnpm dev:web`; workers can run separately with `EMAIL_ADAPTER=capture pnpm dev:worker` for local tests. Never start a live email adapter merely to verify synthetic guest flows.

Guests belong to explicit households. Named people and allocated plus-one slots have per-event eligibility; groups grant no access. Household invitation links use URL fragments, separate hashed private credentials and HttpOnly guest sessions. Owners can rotate/revoke grants without changing the wedding URL; this invalidates associated sessions immediately. Admission and dedicated upload credentials remain separate namespaces/operations.

CSV columns: `household,name,email,phone,group,event_ids,plus_ones`; optional `party_id` explicitly joins an existing household. Separate event UUIDs with `|`; quote CSV fields containing commas/newlines/quotes, double embedded quotes. Maximum 1000 rows per import. Preview validates each row and exposes duplicates; explicitly choose a separate person or skip. Email alone never merges people. New household labels group rows within one import; they do not silently attach to an existing similarly named household. Result lists accepted/rejected/unchanged rows. Exports escape spreadsheet formulas. Standard exports exclude optional sensitive answers; only owners/co-owners can explicitly export/view those answers.

Guests submit the complete allocated party for one event. Expected response/attendee versions detect conflicts. Required `Idempotency-Key` UUIDs scope retries by grant/wedding/event and reject changed payloads. Server time checks deadlines. Party then event locks serialise changes and capacity; confirmed attendees have unique reservations. Automatic attendance reserves capacity or waitlists. Manual attendance stays pending until an owner approves and reserves a place. Declining releases unused reservations and revokes unused passes; admitted attendees require owner corrections. Pass issuance must never reserve capacity again.

The RSVP page shows eligible published event facts, never unpublished website edits. Live RSVP deadlines/approval policy remain authoritative. A private event requires website publication before its details appear; existing public snapshots support old published events. Private facts live in a separate publication projection and never enter the anonymous website payload.

Questions default off. Owners enable necessary meal/dietary/accessibility/note questions and can delete answers. The guest page explains visibility. Confirmation is displayed after the transaction regardless of email delivery. Invitation sending requires a reviewed household recipient set and current grant; duplicates for the same grant/recipient are suppressed. Email is queued, not reported delivered without provider evidence.
