# Portable deployment contract

Three independently runnable Node 22.23.x processes: Next.js web, NestJS API, worker. PostgreSQL 16 supplies transactions, sessions, tenant records, job leases and migrations. An HTTPS reverse proxy exposes one public origin; the API is private to the gateway. Do not expose API port 4000 directly without equivalent TLS/origin/session protections. Static-only hosting is unsupported.

`docker compose up --build` is the provided local container profile at http://localhost:3002, using private local volumes, a private ClamAV scanner, and capture-only email. STD_WEB_PORT/STD_PUBLIC_ORIGIN configure its public localhost address; STD_RENDER_BROWSER_ENDPOINT optionally selects a private dedicated browser. Never use its development keys/passwords publicly. R0 API image built on a generic Linux container using the cached official Node 22.23.2 base; the default image is pinned to its manifest digest. Database-backed /api/v1/health passed from the container against the isolated local database. Native process startup passed too. Web public and .next/static assets are copied into the standalone tree during the supplied image build. Full web/API/worker/PostgreSQL/scanner startup, capture verification, tenant publication and actual queued JPEG/PDF downloads passed in the isolated std-r3-verification project on 2026-10-13. Docker Desktop requires the dedicated-browser option because its sandbox namespaces are denied; see render-browser.md.

Production: supply DB_CONNECTION for a supported PostgreSQL host with verified TLS; PUBLIC_ORIGIN as HTTPS; API_INTERNAL_ORIGIN; TOKEN_HASH_KEYS from protected random secret material; production EMAIL_ADAPTER and sender credentials (or disabled); durable STORAGE_ROOT shared by API/workers or a tested object adapter; explicit RETENTION_POLICY/BACKUP_POLICY identifiers. Production configuration rejects capture email, development keys and /tmp storage. Retention enforcement and recovery-safe erasure run in the API/worker; policy identifiers still document deployment intent and required backup/recovery arrangements.

Run `pnpm db:migrate` once as an authorised release job with a recoverable backup. All replicas must share the same database and secrets. Mount storage directories writable by the Node runtime user. Never build secrets into images. Configure process restart, readiness on /api/v1/health and liveness checks independently. Restrict outbound access and least-privilege database/storage credentials. API readiness performs a real database query. Current health reports optional AI as disabled.

Before R3: complete the encrypted database/object/deletion/admission restore drill, security/load/browser/device/human gates and authorised provider smoke checks. Key rotation, native media processing, real two-adapter storage conformance and dedicated rendering are verified locally. This evidence does not authorise production deployment.

Client attribution: configure the ingress overwrite, WEB_CLIENT_IP_HEADER and exact API_TRUSTED_PROXY_CIDRS together only after isolating web/API network paths. Defaults trust no forwarding headers. See web-security.md; broad trust or an externally accessible web port allows spoofing and is unsupported.

Production API transport: set `PLATFORM_RUNTIME_ENV=production` in every process, separately from Next.js's production-build `NODE_ENV`. Set `API_INTERNAL_ORIGIN=https://<private-api-host>:4000`. Mount `API_TLS_CERT_PATH` and `API_TLS_KEY_PATH` in the API container/process, readable only by its runtime user; production API startup refuses missing keys. The certificate must cover the exact internal hostname. For a private CA, mount its public certificate in the web process and set `API_TLS_CA_PATH`; public trust chains need no override. The gateway verifies trust and hostname, requires TLS 1.2 or later, preserves streaming uploads/downloads and separate session cookies, and refuses HTTP in production mode (also when PUBLIC_ORIGIN is HTTPS). Workers need no API private key. Never disable certificate verification. Certificate renewal/restart, public HTTPS ingress and production network isolation remain deployment checks. The local compose profile deliberately uses development mode and private HTTP.

Production database transport: DB_CONNECTION must explicitly contain `sslmode=verify-full`; encryption-only or disabled modes are refused. For a private CA append `sslrootcert=/run/secrets/db-ca.pem` (URL-encode the path if necessary) and mount the public CA in every database-using API/worker/migration process. Publicly trusted database certificates need no CA path. The installed node-postgres driver verifies the actual server hostname. `node --import tsx scripts/verify-postgres-tls.ts` starts a dedicated throwaway PostgreSQL16 container and proves TLS plus rejection of untrusted/mismatched certificates, then removes its container/files; it never uses DB_CONNECTION. Docker and openssl are required for this optional transport conformance check.
